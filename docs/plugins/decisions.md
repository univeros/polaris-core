# Decisions log (plugins and the packages built on them)

Append one entry per decision. Format: date, work package, decision, reason, alternatives rejected. Task 1's
log is `../extraction/decisions.md`, task 2's `../adapters/decisions.md`.

## Log

- 2026-09-11 · WP0 · The plugin contract is `Polaris\Contract\Plugin` (`id`, `schema`, static `manifestDirectory`, `services`, `listeners`, `permissions`, the last through `PermissionContributorInterface`) with `Polaris\Plugin\AbstractPlugin` for the defaults; `Config::$plugins` carries the instances; `Polaris::create()` wires them. Registration of a plugin's models is static (`Schema::register()`), idempotent by class, because `Schema::for()` is static and used by the unit of work and four services; making the schema instance-based would be a refactor with no behaviour gain. Plugins are therefore "known once `Polaris::create()` ran", documented. A plugin redefining a core class or table is rejected. · Rejected: an instance-based schema registry; `target-design.md` §3.2's `requires()`, `routes()` as objects, `hooks()` and `extensions()` (routes are the manifest already; hooks come with the first package that needs a veto point; extension fields are side tables, below).
- 2026-09-11 · WP0 · `manifestDirectory()` is static so a host's route table (Laravel's provider, Symfony's route loader, Yii's `routes.php`) can be built from class names before a plugin is configured; `Loader` takes several directories and checks route uniqueness across them; spec file names stay relative to their directory, so a plugin keeps its specs under `api/<id>/` and the adapters' route names (`polaris.<id>.<file>`) cannot collide. Plugin endpoints resolve their constructor parameters from the plugin's `services()` factories (built once per graph, `Graph::get()`), after core's services.
- 2026-09-11 · WP0 · Errors of plugin routes are RFC 9457 problem documents (`Endpoint::problem()`, `Result::$problem`, `application/problem+json`) that also carry `error` and `message`, so the generated client's `ErrorBody` and every existing consumer keep working; core's 52 routes keep their plain envelope, frozen. Problem types are URLs under `https://polaris.univeros.io/problems/`. · Rejected: problem documents on core's routes (a behaviour change of the frozen contract); plain envelopes for plugins (no standard shape for new consumers).
- 2026-09-11 · WP0 · No extension fields on core tables: a plugin that needs per-user state (an activity timestamp) keeps it in its own table keyed by the user id. · Reason: plugins own only what they declare; `schema:diff` stays a comparison of declared models.
- 2026-09-11 · WP0 · The CLI sees plugins through `--bootstrap=<file>` (`POLARIS_BOOTSTRAP`), a PHP file returning the application's `Polaris` or `Config`; `schema:create` seeds the plugins' permissions through the graph's catalog (`SchemaInstaller::create(..., catalog:)`). · Rejected: a `POLARIS_PLUGINS` class list (plugins take configuration; a file is the honest unit).
- 2026-09-11 · WP0 · Plugin fixtures are recorded, not written: `Fixture` records raw steps when `POLARIS_RECORD_FIXTURES` is set and no file exists, into the package's own `tests/Contract/fixtures` (`FunctionalTestCase::fixtureDirectory()`), and replays them afterwards through every harness; `FunctionalTestCase::plugins()` selects the plugins a package's tests run with. `ContractCoverageTest` keeps asserting core's 52 routes and 1,201 steps.
- 2026-09-11 · WP1 · `polaris/audit` is a plugin and nothing else: its tables (`polaris_audit_event`, `polaris_audit_drain`, `polaris_audit_activity`), its three routes under `api/audit/`, its services, its two listeners (the recorder, the activity tracker) and its commands all come through the plugin contract; core's `auth_audit_log` and `AuditLogListener` stay as they are (nothing in the frozen contract reads them; a later major may retire them). Ids are UUID v7 like the rest of Polaris (time-ordered, so the cursor is the last id), not ULIDs. The catalog's names are core's 35 events renamed to `namespace.past_tense` (`session.signed_in`, `mfa.challenge_failed`), plus `audit.pruned` for the checkpoint. · Rejected: a second write path through the unit of work (the adapter's `insert` and `findMany` are enough and keep the identity map out of it).
- 2026-09-11 · WP1 · Activity is a side table written from the sign-in, refresh, MFA and organization-switch events, debounced through the cache; there is no per-request hook for plugins in the PSR-15 pipeline and the events carry what "active" means here. Drains are stored and delivered by this package (encrypted secret, name filter, per-drain outcome), their management routes come with `polaris/admin`. Delivery is synchronous after commit; a queued dispatcher is left to the adapters when a host asks for one. A closed time range applies its upper bound in the store after the read, because the adapter takes one condition per column.
- 2026-09-11 · WP1 · Plugin commands: `Polaris\Cli\CommandProvider` (`commands(Graph)`), added by `bin/polaris` when `POLARIS_BOOTSTRAP` names the application; the adapters' consoles register a plugin's commands in a follow-up. Plugin fixtures: the functional base registers a package's plugin schemas before the database base builds the tables, and the recording dispatcher runs `Polaris::listeners()` so the recorder sees the events the endpoints emit.
- 2026-09-11 · WP2 · `Plugin::middleware(Graph)` is the runtime seam `polaris/admin` needed: PSR-15 middleware appended by `Pipeline::middleware()` right after `TokenAuthenticationMiddleware` (core requires `psr/http-server-middleware`); the adapters run the pipeline, so a plugin's middleware runs in every host. Admin routes are declared `auth: public` and tagged `admin`: core's bearer middleware would reject an API key, so the plugin's middleware resolves the principal (an API key, a user's grant, or the superadmin role) and attaches it as a request attribute; the endpoints answer the problems (`admin/unauthorized`, `admin/forbidden`, `admin/impersonation_denied`). · Rejected: a second bearer scheme in core (the 52 routes are frozen); a hook in `TokenAuthenticationMiddleware` (a plugin-specific branch in core's middleware).
- 2026-09-11 · WP2 · Core friction logged for the admin package, kept minimal: `AccessTokenClaims::$extra` (claims a package adds, the standard claims winning) and `TokenService::mint(principal, sessionId, extra)` (public; `issue`, `stepUp`, `switchOrganization` and `refresh` mint through it unchanged); `UserAdminService::anonymize()` split out of `erase()`, which still asserts self-or-`users.manage` and then calls it. No other core change: ban and unban are `disable`/`enable`, sessions are `SessionService`, member roles and MFA reset are written by the plugin through the repositories and the unit of work because the core services check the actor's RBAC authority, which an API key does not have.
- 2026-09-11 · WP2 · Impersonation is an access token, not a session: `sub` the user, `amr: ["impersonation"]`, `mfa: false`, `impersonated_by` and `impersonator_type` claims, no `sid`, so it cannot be refreshed, stepped up, switched or logged out and lives one access-token TTL (15 minutes by default, under the spec's one-hour ceiling; a longer window would need a second token configuration). It carries the user's real authority on core's routes and none on the admin routes; a superadmin cannot be impersonated; a disabled account is refused. · Rejected: a refresh-token family flagged as impersonation (a session that outlives the operator's intent, and a change to core's refresh path).
- 2026-09-11 · WP2 · Principals: one grant per user (a new grant replaces it), so a user resolves to one role and one scope; a scope is `instance` or an organization id, and an organization-scoped principal may call the organization routes of that organization only (the user, key, grant and stats routes need the instance scope). API keys are `pak_` plus 256 random bits, hashed with the pepper (context `admin_key`), shown once, with an IP allowlist (addresses or CIDR blocks, both families) and an expiry; `last_used_at` is stamped on use. A superadmin is an owner without a grant. · Rejected: several grants per user (one scope per principal keeps the checks a single comparison); a JWT for API keys (an opaque hashed secret is revocable at once and needs no key rotation).
- 2026-09-11 · WP2 · Audit: the `admin.*` names are registered on the audit catalog when the plugin builds its middleware or its recorder (the audit plugin must be registered); the operator is the actor (`admin` or `api_key`), the target the subject, the role and scope in `data`; the core event of the action (`user.disabled`, `mfa.factor_removed`, `org.member_roles_changed`) is emitted too, with the principal id as its actor. A drain test records `admin.drain_tested` for the organization through the normal path (delivered when the audit plugin has an HTTP client) and answers the drain's state afterwards, rather than a delivery path of its own. Statistics are counts on the audit tables (`polaris_audit_event`, `polaris_audit_activity`) and core's; the spec's roll-up table, graph, retention and map routes are left for a later package release. · Rejected: a stats cache (counts are indexed; a host above ten million events will need the roll-up anyway).
- 2026-09-11 · client · A package's routes reach the TypeScript client as a namespace named after the plugin (`client.audit.*`, `client.admin.*`), one method per endpoint class, generated from the OpenAPI document: `EndpointSpec::$plugin` (the spec directory) marks a plugin's operations with `x-polaris-plugin`, their operation ids carry the plugin id (`get_audit_MeEndpoint`, so a plugin's `MeEndpoint` cannot shadow core's), their errors are the `Problem` schema as `application/problem+json`, and `list<x>` fields are arrays. The client is generated for an application declared in `packages/client-ts/polaris.php` (core with the audit and admin plugins); every later package adds itself there and gets its namespace without client code. Core's 52 routes keep their path-based calls (`client.POST("/auth/login")`) unchanged. A dashboard is a consumer of the client in its own repository, never UI code in this one. · Rejected: hand-written namespaces (drift); a generic `client.plugin("admin").call(...)` (untyped).
- 2026-09-11 · WP3 · A plugin may provide a core port: `Graph::mailer()`, `sms()`, `breachCheck()` and `metrics()` resolve `config ?? the plugin service keyed by the contract ?? the default`, so `polaris/messaging` takes over the mail and SMS ports without a change to the Config or the adapters (a host that sets its own mailer keeps it). Core's ten template names map onto the package's keys in `Bridge\Mailer`; core's SMS text goes as `sms.otp` unchanged (core renders the code message itself, the bridge cannot recover the code). · Rejected: a `Config::$messaging` field (a plugin-specific field in core); replacing `NotificationListener` (the frozen behaviour stays in core).
- 2026-09-11 · WP3 · Templates are strings with `{placeholders}` (subject, text, optional HTML, escaped) resolved organization override → instance override → the locale's bundled strings → the default locale's, through a `Translator` contract with a bundled array translator; no template engine. The recipient's locale is the plugin's default (core knows no locale; an organization's override is the branding seam); a locale resolver comes when a host needs one. Fallback from SMS to email needs the alternative address, which core's OTP path does not carry: it serves the application's own sends and is logged as such. `messaging.sent` is an `Auditable` event (channel, template, recipient hash, provider id, never the body). No routes in this release; organization overrides are written through `Templates::set()` until an admin route is asked for. · Rejected: a functional fixture suite (the package has no routes; the bridge is proven through `Polaris::listeners()` in memory).
- 2026-09-11 · release · The sibling constraint moves with each minor: at 0.3.0 the packages require each other at `^0.3` and the path repository and the demos use `0.3.x-dev`, as the 0.2 line did (#28). `^0.2` excludes 0.3.0, so a package tagged 0.3.0 could not have been installed next to core 0.3.0. Every release bumps the line.
- 2026-09-11 · WP4 · `polaris/sentinel` needs no Before* hook in core: its PSR-15 middleware (the WP2 seam) runs on the guarded routes (`/auth/register`, `/auth/login`, `/auth/password/forgot`, `/auth/email/verify/resend`, `/auth/mfa/challenge`) before the endpoint, with the body, the client address, the user agent and the device cookie, and answers the block or challenge problem itself; the outcomes come from `UserLoginFailed` and `UserLoggedIn` through a listener. Zero core change. · Rejected: a `Guard` seam in the registration, login, password-reset and OTP services (four core edits for what the pipeline already offers).
- 2026-09-11 · WP4 · The challenge is a captcha only: `sentinel/challenge_required` carries `challenge: captcha` and the client retries the same request with `captcha_token`, which the `bot` signal verifies (a passed challenge turns a challenge into an allow and is listed with the signals that spoke; a wrong token scores as a bot). Without a `BotVerifier` nothing can answer a challenge, so the middleware records the challenge band and lets it through, documented. · Rejected: a step-up through core's MFA or an email OTP (a session-less request has nothing to step up; the OTP send is itself a guarded route).
- 2026-09-11 · WP4 · Only decisions where a signal spoke are recorded (`polaris_sentinel_decision`, `sentinel.evaluated`): silence on every attempt would write a row per sign-in for nothing an operator can act on; the audit event carries the email hashed and never the password or the token. Blocks answer a generic detail; the reason stays in the record. A signal that throws is skipped and logged: the engine fails open, because a provider outage must not lock an instance out.
- 2026-09-11 · WP4 · The middleware answers with a PSR-17 response factory: the one the plugin is given, otherwise a discovered one (httpsoft, laminas, nyholm, guzzle, whichever is installed), because core's `Config::$responseFactory` is not exposed by the graph and the middleware runs before the pipeline's own responder. The device cookie is set by the middleware on the first response, one year, `HttpOnly`, `SameSite=Lax`, `Secure` on https.
- 2026-09-11 · WP4 · The operator routes hang under `/admin/sentinel`, tagged `admin` and declared `auth: public`, so `polaris/admin`'s middleware resolves the principal and its `AdminRoute` answers the `admin/*` problems; the rules are instance-wide and need the instance scope; reads need `read`, the rules `own`, unblock `support` (a support agent clears a locked-out person's counters; a rule is policy). The operators' actions are `sentinel.ip_rule_created|deleted` and `sentinel.unblocked`, recorded through the admin plugin's recorder with the principal as actor.
- 2026-09-11 · WP4 · `Graph::port()` is public so `polaris/messaging` takes the sentinel's `Suppressor` (quiet mode: no non-essential message to a recipient challenged or blocked in the last hour) when the host passes none; a host's own suppressor still wins. - 2026-09-12 · WP5 · `polaris/sso` is written fresh (core has no SAML or OIDC). SAML through `onelogin/php-saml` 4 in strict mode behind `Polaris\Sso\Saml\SamlProtocol`, OIDC through PSR-18 and `firebase/php-jwt` (JWKS parsing, leeway) behind `Polaris\Sso\Oidc\OidcProtocol`; both are package requirements, not suggestions, because SAML and OIDC are the package; a host or a test passes its own implementation. The library compares the SAML Destination with `$_SERVER`, so it runs with `relaxDestinationValidation` and the package checks the Destination against the SP URLs itself; `baseurl` is the plugin's `baseUrl` (where Polaris is mounted, prefix included), from which the SP entity id, ACS, SLO and metadata URLs derive. IdP logout requests must be signed (the redirect binding's query signature or an enveloped one), or anyone naming an email could end its sessions. · Rejected: a hand-written SAML SP (security-critical XML signature handling); lcobucci/jwt for the id_token (PEM keys only, no JWKS).
- 2026-09-12 · WP5 · The sign-in ends with a hand-off: the callback opens the session and answers `302 <redirect_uri>?sso_code=...`; `POST /sso/exchange` turns the code (one minute, once, hashed in the cache) into core's login envelope. The session is scoped to the provider's organization with `amr: ["sso"]`, the principal resolved by core's RBAC resolver. · Rejected: the login envelope on the callback (the browser lands there); tokens in the fragment (they leak into history and referrers).
- 2026-09-12 · WP5 · Short-lived state (OIDC state, nonce and PKCE verifier; SAML request ids; assertion ids seen until they expire plus the drift; hand-off codes) lives in the graph's PSR-16 cache under `polaris.sso.*`, not in a table: it is minutes-old by nature and a shared cache is what a multi-node host already runs for the rate store. A cache flush forgets the replay set for the remaining assertion validity; documented.
- 2026-09-12 · WP5 · Provisioning: a user found by the asserted email signs in (disabled refuses); an unknown one is created when the provider's `jit.enabled` is set, with the email verified because the IdP vouched for the mailbox and no password; the membership is created with the roles of `jit.roles` (`member` by default), through the unit of work as `InvitationService::accept` writes it, with `MemberJoined`; a suspended membership refuses. - 2026-09-12 · WP6 · `polaris/scim` is written fresh (core has no SCIM). A SCIM User is a Polaris user with a membership in the connection's organization and a SCIM Group is one of the organization's roles; both keep Polaris's ids, so a person keeps one id across connections. Users are written as `polaris/sso` writes them (verified, no password, the `member` role, `MemberJoined`); roles directly through the unit of work, because `RoleService::create` checks an actor's `roles.manage`, which a directory does not hold; deactivation and anonymisation go through `UserAdminService::disable/enable/anonymize` with the actor `scim`. The built-in `owner`, `admin` and `member` roles (cloned per organization, `is_system` false) are protected by slug from renaming and deletion. · Rejected: teams (core has none); a separate SCIM user table (a second identity for the same person).
- 2026-09-12 · WP6 · Provenance: `polaris_scim_membership_provenance` records the memberships a connection created and those are the only ones it removes; a member who predates the connection is deactivated on deprovisioning but keeps the membership; a decommissioned connection leaves everyone in place. `deprovision` is per connection: `deactivate` (the default: banned, sessions ended) or `delete` (anonymised), the spec's "never hard-deleted unless the connection says so".
- 2026-09-12 · WP6 · Connections are plugin-managed only: a `pst_` token (256 random bits, `Pepper`-hashed like the admin keys) created, rotated and decommissioned by the organization under `/orgs/{id}/scim/connections` (`org.update`, the active-organization guard), shown once; the plugin's middleware (the WP2 seam) resolves the bearer on the routes tagged `scim` and the endpoints require it to be the path's connection. The spec's static and application-verified modes are a row a host writes itself; logged as not built. Filters are the subset directories send when they look a resource up (`eq`, `co`, `sw`, `and`); everything else is `invalidFilter`. Members are loaded and filtered in memory (a `ponytail:` note marks the ceiling).
- 2026-09-12 · WP6 · SCIM routes answer SCIM documents and SCIM error documents (RFC 7644 §3.12, `application/scim+json`) rather than problem documents, because the callers are directories that read the standard shape; `error` and `message` ride along for the generated client. A `204` carries no content type (core's JSON responder, because HttpFoundation drops one on an empty response and the fixtures must match across hosts); the Yii test application parses `application/scim+json` as JSON and the README tells a Yii host to do the same.
